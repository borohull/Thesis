\section{Motivation}
\label{sec:intro-motivation}

Students and staff at the Faculty of Informatics of Eötvös Loránd University
face a recurring practical challenge: finding accurate answers to questions
about the curriculum. Which courses must be completed before enrolling in a
given subject? What are the rules for repeating a failed exam? The answers
exist --- scattered across faculty web pages, PDF regulations, and DOCX course
descriptions --- but locating the right document and extracting a clear answer
takes considerably longer than it should.

General-purpose search engines return ranked lists of pages; they do not
synthesise an answer from multiple sources or understand the specific
terminology of Hungarian higher education. As documentation grows each
semester and more information migrates to hard-to-find sub-pages, the gap
between the information that exists and what students can efficiently find
continues to widen.

\section{Related Work}
\label{sec:intro-related}

Several universities have built AI-powered platforms that demonstrate the
viability of language models in higher education. Examining them critically,
however, reveals a consistent set of design assumptions that make them
fundamentally different from the system developed in this thesis.

\textbf{UM-GPT} (University of Michigan) is a university-wide platform on
Microsoft Azure offering access to multiple large language models, with a
companion RAG tool, Maizey, that lets any user build a chatbot from a custom
dataset~\cite{umich_genai}. While Maizey shares the same retrieval mechanism
as this system, it is general-purpose: users define their own knowledge base
and purpose, rather than targeting a specific institutional need.

\textbf{ZotGPT} (UC Irvine) includes ClassChat, which allows instructors to
configure an AI assistant around their course materials~\cite{uci_zotgpt}.
Its orientation is pedagogical --- it supports teaching within a classroom
context and does not address the broader institutional information problem
that students navigate independently.

\textbf{CreateAI} (Arizona State University) aggregates over 50 AI models
into a single platform for building custom applications across the entire
university~\cite{asu_createai}. Its breadth is also its limitation: a
platform spanning dozens of unrelated domains is not optimised for precise
retrieval over a single faculty's document corpus.

A common profile emerges across all three: cloud infrastructure,
general-purpose scope, and significant IT investment. None target a fixed
domain-specific corpus, and none were evaluated on whether they correctly
answer the institutional questions students actually ask. This is the gap
the present work addresses.

\section{Problem Statement}
\label{sec:intro-problem}

The related systems above establish that LLM-powered question answering is
viable in higher education, but they do not provide a usable template for
the ELTE Faculty of Informatics. Two concrete problems block direct adoption.

\paragraph{Domain knowledge and hallucination.}
General-purpose LLMs have no knowledge of ELTE-specific regulations, course
codes, or administrative procedures. Without grounding in official faculty
documents, a language model will hallucinate plausible-sounding but incorrect
answers --- a particularly harmful failure mode when a wrong answer about
prerequisites or exam rules has real consequences for a student's progress.

\paragraph{Resource and infrastructure constraints.}
Deploying a cloud-hosted platform requires dedicated IT teams and substantial
recurring costs that a single faculty cannot sustain. Any practical solution
must run on commodity hardware with no GPU and no cloud subscription.

No dedicated question-answering system currently exists for the ELTE Faculty
of Informatics. Students rely on web search, email queries to administrative
offices, or peer advice --- all slow, inconsistent, and unscalable.

\paragraph{Approach: retrieval-augmented generation over fine-tuning.}
The original project specification proposed fine-tuning a small language model
on faculty documents. During the design phase this approach was set aside for
three reasons. First, fine-tuning requires labelled question-answer training
pairs, not raw documents; constructing a dataset of sufficient quality and
breadth would itself have been a substantial project. Second, a fine-tuned
model is static: every time a regulation changes or a new course is added,
the model must be retrained from scratch. Third, factual recall in fine-tuned
sub-4B models is unreliable --- small models trained on small corpora tend to
hallucinate rather than reproduce memorised facts accurately. Retrieval-augmented
generation addresses all three problems: it requires no training data, updates
by re-indexing rather than retraining, and grounds each answer in a retrieved
passage rather than relying on parametric memory. All goals stated in the
original specification --- local deployment, privacy, low cost, and accurate
faculty-specific answers --- are preserved under this design.

\section{Objective}
\label{sec:intro-overview}

The result of this work is a web-based chatbot for the ELTE Faculty of
Informatics. It crawls the faculty website, indexes the collected documents
into a local vector database, and answers student questions in natural
language by retrieving relevant passages and generating grounded responses
through a locally running language model. The entire system runs on a
standard laptop with no GPU and no cloud dependency.

This thesis designs, implements, and evaluates a locally deployed
question-answering system for the ELTE Faculty of Informatics, built on
retrieval-augmented generation. The goal is to provide accurate,
document-grounded answers to student questions without the infrastructure
investment or general-purpose scope of the platforms examined above. The
specific goals are:

\begin{itemize}
  \item Collect and index publicly available faculty documents --- web pages,
    PDFs, and course descriptions --- into a searchable local knowledge base.

  \item Answer natural language questions by retrieving relevant document
    passages and generating grounded responses, rather than relying on the
    general knowledge of a language model.

  \item Run entirely on commodity hardware without a GPU or cloud
    subscription.

  \item Provide a browser-based chat interface with source references so
    users can verify and follow up on every answer.

  \item Evaluate the system empirically against a no-RAG baseline to measure
    whether retrieval meaningfully improves answer accuracy.

  \item Deploy as a ready-to-run web service, so that moving to a faculty
    server requires infrastructure provisioning only, with no code changes.
\end{itemize}

\section{Technologies Used}
\label{sec:intro-technologies}

Two hard constraints shaped every technology decision: the system must run
on commodity hardware with 8~GB of RAM and no discrete GPU, and no query or
document may leave the local machine. The following components form the
complete stack.

\begin{itemize}
    \item \textbf{Ollama} serves large language models locally over a REST
        interface, handling quantisation and memory mapping automatically.
        Switching models requires only a one-line configuration change.

    \item \textbf{Llama~3.2~(3B) and Gemma~3~(4B)} are the two open-weight
        models evaluated in this thesis. Both run at 4-bit quantisation,
        reducing their memory footprint to approximately 2--2.5~GB and
        making CPU-only inference feasible.

    \item \textbf{all-MiniLM-L6-v2} encodes document chunks and user queries
        into 384-dimensional vectors for semantic similarity search, running
        efficiently on CPU.

    \item \textbf{ChromaDB} stores chunk embeddings and answers
        nearest-neighbour queries at runtime. It runs in-process with no
        separate server and persists to a plain directory on disk.

    \item \textbf{FastAPI} exposes the RAG pipeline as a REST API and serves
        the browser interface as static files, chosen for its low boilerplate
        and built-in request validation.

    \item \textbf{SQLite} logs every interaction --- query, answer, sources,
        and response time --- to a single file on disk with no server process
        or configuration required.

    \item \textbf{Vanilla JavaScript} powers the browser interface as a
        single self-contained HTML file. Avoiding a frontend framework
        eliminates a build step and all Node.js dependencies entirely.

    \item \textbf{Docker} packages the entire stack into isolated containers,
        so that moving from a local machine to a faculty server requires
        infrastructure provisioning only, with no code changes.
\end{itemize}

\section{Thesis Structure}
\label{sec:intro-structure}

The remainder of this thesis is organised as follows.

\textbf{Chapter~\ref{ch:requirements}} defines the system requirements. It states
the functional requirements covering the capabilities exposed to the user, and the
non-functional constraints including resource limits, latency, privacy, and offline
operation.

\textbf{Chapter~\ref{ch:user}} provides user documentation: a use-case diagram, step-by-step
instructions for the web interface and command-line client, and annotated example queries.

\textbf{Chapter~\ref{ch:devdocs}} covers developer documentation. It describes the system
architecture and component design, then details the full implementation across the data
pipeline, embedding, RAG backend, REST API, logging, frontend, and deployment.

\textbf{Chapter~\ref{ch:testing}} presents the testing and evaluation of the system. It covers
functional testing, the empirical RAG vs.\ baseline evaluation, and a user evaluation.

\textbf{The Conclusion} summarises the findings, reflects on the key design decisions, and
outlines directions for future work.
