\chapter{Software Requirements}
\label{ch:requirements}

The system must run fully offline on commodity student hardware, require no cloud services, and answer faculty-related questions from a locally indexed document corpus.

% ─────────────────────────────────────────────────────────────
\section{Functional Requirements}
\label{sec:req-functional}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.8\textwidth]{UseCaseDiagram.png}
    \caption{Use case diagram for the ELTE IK Assistant}
    \label{fig:use-case}
\end{figure}

The primary interactions within the system are illustrated in Figure~\ref{fig:use-case}. The main functional capabilities include:

\begin{itemize}
    \item \textbf{Natural language querying:} the system accepts a free-text English question and returns a textual answer with source citations. When the answer is absent from the indexed documents, the system must say so explicitly.

    \item \textbf{Document ingestion:} the pipeline loads HTML, PDF, and DOCX files, cleans and chunks the text, and persists the result for the embedding step. Only new or modified files are re-processed, detected via content hash.

    \item \textbf{Embedding and retrieval:} each chunk is encoded into a dense vector and stored in a local persistent vector database. At query time the top-$K$ most similar chunks are retrieved; $K$ is configurable.

    \item \textbf{Answer generation:} retrieved chunks are assembled into a prompt that constrains the model to answer only from provided context. Inference runs locally with no external API calls.

    \item \textbf{REST API:} the backend exposes a \texttt{/health} endpoint reporting system status and a \texttt{/chat} endpoint that accepts a message and returns the answer with source references.

    \item \textbf{Web interface:} a browser-based chat UI displays conversation history, source file names, model availability, and inline error messages.

    \item \textbf{Interaction logging:} every interaction is recorded to a local database, including the query, answer, sources, response time, and any errors, to support offline evaluation.
\end{itemize}

\section{Non-Functional Requirements}
\label{sec:req-nonfunctional}

\begin{itemize}
    \item \textbf{Privacy:} no query, chunk, or answer may leave the local machine. The system must remain fully functional in a network-isolated environment after initial setup.

    \item \textbf{Resource constraints:} the system must run on 8~GB RAM with no discrete GPU, using a quantised (4-bit or 8-bit) language model and a CPU-friendly embedding model.

    \item \textbf{Response latency:} end-to-end response time must not exceed 90~seconds on the reference hardware. Embedding and retrieval complete in under one second; generation typically takes 30--80~seconds on CPU.

    \item \textbf{Offline operation:} after the initial model pull and corpus crawl, no network connection is required. All subsequent pipeline steps run entirely from local storage.

    \item \textbf{Reliability:} if the language model process is unavailable, \texttt{/health} must report it and \texttt{/chat} must return an HTTP~503. The vector store and log database must not be corrupted on unexpected shutdown, and re-running the pipeline must be idempotent.

    \item \textbf{Configurability:} all tunable parameters — model names, $K$, temperature, paths, timeouts — are defined in a single configuration module. Swapping models requires only a one-line change there; changing the embedding model additionally requires rebuilding the vector store.
\end{itemize}
