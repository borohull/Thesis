\chapter{Developer Documentation}
\label{ch:devdocs}

This chapter covers the full developer documentation for the ELTE IK
Assistant. It is divided into two parts: the design section describes the
system architecture, key design decisions, component structure, and storage
model; the implementation section details how each layer was built.

% ─────────────────────────────────────────────────────────────
\section{Design}
\label{sec:design}

This section describes the architecture of the ELTE IK Assistant, the
reasoning behind its key design decisions, the module structure of the
application, and the storage model used to persist data.

% ─────────────────────────────────────────────────────────────
\subsection{System Architecture}
\label{sec:design-overview}

The ELTE IK Assistant is organised as three layers:

\begin{enumerate}
    \item \textbf{Data pipeline} — a standalone crawler script downloads
    raw documents from the ELTE websites; a separate ingestion and embedding
    pipeline cleans, chunks, and encodes those documents into vector embeddings,
    then stores them in a local vector database. This pipeline is run once by
    the system administrator and re-run whenever the source documents change.
    \item \textbf{Online serving layer} — a FastAPI web server that accepts a
    user's natural-language question, retrieves the most relevant document
    chunks from the vector database, builds a prompt, calls a locally running
    language model, and returns the generated answer together with source
    references.
    \item \textbf{Presentation layer} — a single-page browser UI that maintains
    session state, renders the conversation, and displays source file metadata
    alongside each answer.
\end{enumerate}

Figure~\ref{fig:architecture} illustrates the high-level data flow between
these layers. The data pipeline (top) is run once to build the vector index;
the online pipeline (bottom) handles every user query at runtime.

The strict separation between the data and online pipelines is a deliberate
consequence of the offline-operation requirement (R-NF-1): once the vector
index is built, the serving layer requires no network access and its only
disk reads are ChromaDB queries and SQLite log operations.

\subsection{Key Design Decisions}
\label{sec:design-decisions}

\paragraph{Local LLM via Ollama.}
Running the language model locally satisfies both the privacy requirement ---
no query or document ever leaves the machine --- and the offline requirement.
The cost is higher latency: on the development hardware, median response times
range from 25 to 180 seconds depending on the model. This trade-off was
unavoidable given the constraints.

\paragraph{Model selection.}
\texttt{llama3.2:3b} and \texttt{gemma3:4b} were selected as the leading
instruction-tuned open-weight models in the sub-5B parameter range available
through Ollama. The 8~GB RAM constraint rules out 7B+ models at 16-bit
precision ($\approx$14~GB); both evaluated models use 4-bit quantisation,
reducing their footprint to approximately 2~GB and 2.5~GB respectively, leaving sufficient headroom for
the embedding model, ChromaDB index, and operating system. Both models also
support instruction-following out of the box, which is necessary for the
grounded-answer prompt to work reliably.

\paragraph{Chunking strategy.}
Documents are split into 800-character chunks with a 150-character overlap.
This size is large enough to contain a complete regulation clause yet small
enough for accurate embedding. The overlap ensures no sentence is silently
dropped at a split boundary.

\paragraph{Top-$k$ retrieval.}
Evaluation was conducted at $k = 5$; the production default was set to
$k = 3$ to reduce inference latency on CPU-only hardware, with minimal
impact on answer quality. At 800 characters per chunk, three chunks contribute approximately 2400
characters of context — well within the context window of both evaluated
models.

\paragraph{Temperature.}
A temperature of 0.1 makes the model near-deterministic, which is
appropriate for a factual assistant. Exactly 0 was avoided due to
degenerate repetition loops observed during development.

\paragraph{Containerisation with Docker.}
Docker Compose packages the entire stack into isolated containers, directly
satisfying the deployability requirement: moving to a faculty server requires
only infrastructure provisioning with no code changes. The manual setup path
remains available for single-machine users.

\subsection{Component Design}
\label{sec:design-components}

The application is composed of five Python modules in the \texttt{app/}
package, each with a single responsibility, plus two data pipeline scripts
that run outside the serving layer. All modules read their tunable parameters
from a shared configuration module (\texttt{app/settings.py}); this
dependency is not shown in Figure~\ref{fig:module-diagram} to avoid
cluttering the arrows, but it applies to every module listed below.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{images/ModuleDiagram.png}
    \caption{Module structure and dependencies of the ELTE IK Assistant.}
    \label{fig:module-diagram}
\end{figure}

\textbf{Data pipeline scripts.} Two scripts build the knowledge base and
are never imported by the serving layer at runtime.
\begin{itemize}
    \item \textbf{Crawler} (\texttt{scripts/crawler.py}) --- breadth-first
    crawl of the ELTE websites; downloads HTML, PDF, and DOCX files into
    \texttt{data/raw/} and maintains a SHA-256 manifest for resumable runs
    (see Section~\ref{sec:impl-sha256}). Re-running the crawler is safe:
    unchanged files are skipped automatically.

    \item \textbf{Build index} (\texttt{scripts/build\_index.py}) reads the
    raw files produced by the crawler, applies format-specific loaders to
    extract clean text, splits the text into overlapping chunks, encodes
    each chunk with \texttt{all-MiniLM-L6-v2} (see Section~\ref{sec:impl-embedding-model}), and
    upserts the vectors into ChromaDB incrementally. Only new or changed
    files are re-processed on each run.
\end{itemize}

\textbf{Serving layer modules.} The following five modules are loaded when
the FastAPI process starts and handle all runtime activity.
\begin{itemize}
    \item \textbf{settings} (\texttt{app/settings.py}) --- all tunable
    constants in one place; no business logic. Every other module imports
    from it, so a single edit propagates everywhere.

    \item \textbf{rag} (\texttt{app/rag.py}) --- core pipeline: encodes the
    query, retrieves top-$k$ chunks, builds the prompt, calls Ollama, and
    returns the answer with source references. The embedding model and
    ChromaDB client are held as singletons, loaded once at startup.

    \item \textbf{ingest} (\texttt{app/ingest.py}) --- chunks and embeds
    user-uploaded files directly into the live ChromaDB collection, making
    them available for retrieval immediately without a server restart.

    \item \textbf{logger} (\texttt{app/logger.py}) --- owns the SQLite
    database; the only module that reads from or writes to it. Records chat
    interactions, sessions, and uploads.

    \item \textbf{main} (\texttt{app/main.py}) --- FastAPI entry point;
    wires HTTP endpoints to the other modules and mounts the static frontend.
    It contains no business logic of its own.
\end{itemize}

\subsection{Storage Design}
\label{sec:design-storage}

The system uses two runtime stores, accessed on every request, and two
build artifacts produced by the data pipeline and consumed during index
construction. All four are plain files on the local filesystem — no
database server, no cloud storage, and no network filesystem are involved.

\begin{table}[H]
    \centering
    \begin{tabular}{|l|l|p{0.40\textwidth}|}
        \hline
        \textbf{Store} & \textbf{Location} & \textbf{Contents and access pattern} \\
        \hline\hline
        ChromaDB & \texttt{data/processed/chroma\_db/} &
            6112 chunk embeddings (384-dim float32) and metadata.
            Written once by the data pipeline; read on every query
            via approximate nearest-neighbour search. \\
        \hline
        SQLite & \texttt{data/logs/chat\_logs.db} &
            One row per chat turn: session id, user message, assistant
            answer, sources, response time, and timestamp.
            Appended on every request; queried for session listing
            and history retrieval. \\
        \hline\hline
        chunks.json & \texttt{data/processed/chunks.json} &
            All document chunks with text and metadata produced by
            the ingestion step. Written by \texttt{build\_index.py}
            after chunking; read by the embedding step to populate
            ChromaDB. Not accessed at runtime. \\
        \hline
        manifest.json & \texttt{data/processed/manifest.json} &
            SHA-256 digests, chunk counts, and timestamps for every
            crawled file. Written and read by the data pipeline to
            detect new, updated, and deleted files during incremental
            re-indexing. Not accessed at runtime. \\
        \hline
    \end{tabular}
    \caption{Runtime stores (above double line) and data pipeline
             artifacts (below double line) used by the ELTE IK Assistant.}
    \label{tab:storage}
\end{table}

Because the entire system state is contained in these four files, the
knowledge base can be backed up or migrated by copying the
\texttt{data/} directory, and the serving layer can be restarted on
any machine that has the directory without rebuilding the index.
